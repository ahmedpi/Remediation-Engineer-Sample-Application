# Agentic SAST — Node JS

## Summary
The application has two independent pre-authentication paths to financial fraud: (1) a hardcoded FauxPay API key combined with non-invalidating card tokens allows arbitrary card charges from the internet with no login, and (2) the absence of login rate-limiting trivially brute-forces the seeded default credentials, escalating to every privileged role. Multiple server-side race conditions (TOCTOU refund, concurrent oversell) and business-logic bypasses compound the financial fraud surface once authenticated. A committed default database password means any container-level code execution — reachable via an unpinned base-image supply-chain attack — yields a full PII and credential dump.

## Threat Model

### System context

Widget Shop is a containerised, multi-tier sample e-commerce application consisting of a Vite/React SPA (web/), an Express REST API (api/), a PostgreSQL database, and a fictional payment-processor stub called FauxPay (fauxpay/). All four services run under Docker Compose with nginx as the edge reverse-proxy on port 8080, routing /api and /fauxpay paths to internal unexposed services. The application models at least four user roles — anonymous, customer, admin, and customer-service agent — with role enforcement gates implemented client-side via RequireRole in React's AuthContext; whether the Express API independently enforces these gates server-side is not determinable from the structural snapshot alone. FauxPay performs card tokenisation, charge, and refund operations against a local mock; the data flows (card numbers in, tokens out, charge/refund RPCs over plain internal HTTP) mirror a production payment integration and carry equivalent sensitivity.

The application is explicitly a sample/development workload: seeded admin and CS-agent accounts share the documented default password 'ChangeMe123!', internal service communication uses plain HTTP (FAUXPAY_BASE_URL=http://fauxpay:4000 in docker-compose), and no hardened deployment configuration — WAF, rate limiting, CSRF middleware, mTLS, or secrets manager — is visible in the manifests. The call graph reveals user-generated content surfaces (product reviews via WidgetDetail.jsx::submitReview), financial mutation surfaces (Admin.jsx::updatePrice, CustomerService.jsx::issueRefund), card-data flows (Checkout.jsx::submit → tokenizeCard), and a FauxPay client that issues charge and refund RPCs (fauxpayClient.js::charge/refund). The sole s1-mapped entry point is Admin.jsx::updatePrice, tagged auth with a STRIDE hint of Tampering and Information-Disclosure.

#### Description
Line 4 reads `const API_KEY = [REDACTED-SECRET] || 'fauxpay_test_key'`. The right-hand operand of `||` is the literal string `'fauxpay_test_key'`. If the referenced environment variable evaluates to an empty string, undefined, or is simply absent from the container's environment, JavaScript's short-circuit evaluation selects the hardcoded fallback. The `requireApiKey` middleware (line 17) then grants access to any caller presenting `[REDACTED-BEARER]`. Because this is a publicly distributed training/demo application, the source is expected to be read by a broad audience, making the fallback value effectively public knowledge. The `/charge` endpoint (line 43) uses this guard to control who may authorise financial transactions and create transaction records that can later be used by `/refund`.

#### Impact
If the container starts without the expected environment variable set, the API key falls back to the publicly-visible string `fauxpay_test_key`. Anyone who has read the source code (a training/demo repository likely to be public) can immediately authenticate to /charge and /refund without any brute-force.

#### Exploit scenario
A developer deploys the Docker Compose stack without setting the FauxPay API key environment variable (e.g., when running from a fresh clone with no `.env` file). An attacker who has read the GitHub repository sends `POST /fauxpay/charge` with `Authorization: [REDACTED-BEARER]` and any card token obtained from the unauthenticated /tokenize endpoint, successfully recording a fraudulent transaction.

- The FauxPay container is started without the API key environment variable set (no .env file, misconfigured deployment, or CI pipeline that doesn't inject secrets)
- Attacker has network access to port 8080 — no credentials or prior access required


**Summary:** The scanner's technical description is fully accurate. The `< 0` guard was written to block negatives but was never extended to block zero. The same gap exists identically on both the frontend and the backend API handler. An admin (including a compromised admin account) can drive any widget's price to $0, making it freely purchasable by all customers until manually corrected. The only barrier is obtaining admin credentials — which are subject to phishing, session hijacking, or insider threat.

## Exploit Chains

### [CRITICAL] Pre-auth hardcoded FauxPay key + non-invalidated token → unlimited arbitrary card charges
**Path:** #2 Hardcoded fallback API key bypasses authentication when env var unset → #7 Card token never invalidated after charge — unlimited replay

Step 1 — Finding 10: FAUXPAY_API_KEY is absent or empty in a dev/demo deployment, so `const API_KEY = [REDACTED-SECRET] || 'fauxpay_test_key'` resolves to the publicly readable hardcoded literal. nginx proxies /fauxpay/* from port 8080 to the fauxpay container, making the endpoints internet-reachable. Step 2 — Finding 15: POST /fauxpay/tokenize requires no authentication (confirmed in the finding); any caller submits card_number, exp_month, exp_year, cvv and receives a token. The token is written into the in-memory Map with no TTL and no deletion path. Step 3 — Finding 10 + 15: attacker sends POST /fauxpay/charge with Authorization: [REDACTED-BEARER] and the captured token. The requireApiKey middleware accepts the hardcoded key; tokens.get() returns the card record; the charge succeeds. Step 4 — Finding 15: the charge handler has no tokens.delete() call, so the token remains valid. The attacker repeats step 3 indefinitely, issuing unlimited charges against the same card. No account, no login, no prerequisites — fully pre-auth financial fraud from the public internet.

### [CRITICAL] Timing email enumeration + unlimited brute-force → account takeover including default admin/CS credentials
**Path:** #13 Timing side-channel enables email account enumeration on login → #1 No rate-limiting or lockout on /auth/login

Step 1 — Finding 0: POST /auth/login returns in ~2-5 ms when the email is unregistered (bcrypt.compare is never called) and in ~60 ms when the email exists but the password is wrong. An attacker binary-searches the user table by timing repeated requests with a fixed wrong password, building a set of confirmed registered email addresses. Step 2 — Finding 1: POST /auth/login has no rate-limit, no lockout counter, and no CAPTCHA. For the seeded admin and CS-agent accounts, the documented default password 'ChangeMe123!' succeeds immediately — no brute-force needed. For discovered customer emails, an attacker sprays credential-stuffing lists at wire speed. A successful login yields a JWT granting full access to the corresponding role's API surface: admin receives price-management endpoints; CS-agent receives the PII dump (finding 4) and refund fraud surface (findings 3, 5, 14).

### [CRITICAL] Brute-force CS auth → exchanged-order status bypass + TOCTOU race + double-submit → unlimited refund fraud
**Path:** #1 No rate-limiting or lockout on /auth/login → #10 Refund Permitted on Already-Exchanged Orders Enabling Double Compensation → #11 TOCTOU race allows refunds exceeding order total → #8 Double-submit race on Issue Refund button causes duplicate charges

Step 1 — Finding 1: Authenticate as the CS-agent account using default credentials or credential-stuffing; no rate-limit prevents this. Step 2 — Finding 5: Identify an order whose status is 'exchanged'. The refund handler at cs.js:27-68 checks only (a) payment record exists and (b) cumulative refund does not exceed order.total_cents. It never reads order.status. An exchanged order satisfies both checks: its payment_id is still live and refundedSoFar = 0 (no prior monetary refunds — only an in-kind exchange was issued). Step 3 — Finding 14: The Issue Refund button in CustomerService.jsx has no loading guard; no flag is set before the first await. A double-click or two rapid programmatic HTTP requests both see the same React state (selected, refundAmount, refundReason) and both invoke the refund endpoint concurrently. Step 4 — Finding 3: On the server, both requests read refundedSoFar = 0 from the same pre-lock snapshot, both satisfy 0 + total_cents <= total_cents, both await the async FauxPay HTTP call (~100-500 ms window with no SELECT FOR UPDATE), and both successfully insert refund rows. Result: 2× the order total is paid out via FauxPay. Net financial exposure per targeted order: exchange compensation already received + 2× monetary refund = 3× the original order value.

### [HIGH] Supply-chain image poisoning → container code execution → full database dump
**Path:** #3 Base image pulled by mutable tag, no digest pin → #4 Trivially-guessable default PostgreSQL password committed to source  
**Blocked by:** requires successful supply-chain compromise or CI/CD pipeline access (AC:H, UI:R in finding 6)

Step 1 — Finding 6: Both FROM node:20-alpine stages in api/Dockerfile have no @sha256 digest pin. Docker resolves the tag at build time against whatever the registry currently serves. An attacker who can influence what node:20-alpine resolves to — via tag overwrite on Docker Hub, a compromised upstream publisher, a poisoned mirror, or direct CI/CD pipeline access — injects malicious code that runs inside the api container on the next image build. Step 2 — Finding 7: Once executing code in the api container, the attacker reads the DB_PASSWORD environment variable. If the production secret was never set (or a .env file was not mounted), the Compose default 'widgetshop' applies. The Postgres port is exposed only on the Docker bridge network, but all Compose services (api, migrate) are on that network. A single `psql -h db -U widgetshop -d widgetshop` yields a full dump of all customer PII, bcrypt password hashes, order records, FauxPay tokens, and any other application data — game over for confidentiality. The chain is gated on finding 6's supply-chain prerequisites but is completely unblocked once that step succeeds.

### [HIGH] FauxPay timing oracle + hardcoded fallback → guaranteed API key recovery in all deployment states
**Path:** #5 Non-constant-time API key comparison leaks timing oracle → #2 Hardcoded fallback API key bypasses authentication when env var unset  
**Blocked by:** timing attack in finding 9 requires many requests and a low-jitter network path (AC:H)

These two findings cover complementary and exhaustive cases. Finding 10: when FAUXPAY_API_KEY is absent or empty, the key is the public literal 'fauxpay_test_key' — trivially known from source without any network interaction. Finding 9: when the env var IS set with a real secret, the `!==` comparison in requireApiKey exits at the first differing byte, leaking the correct key character-by-character via median response time measurements. An attacker tries all possible next-character values at each position, identifies the one that takes measurably longer to reject, and iterates until the full key is reconstructed. Together these two findings eliminate both deployment states as safe: env var absent → finding 10 gives the key instantly; env var set → finding 9 recovers it via timing. A recovered key grants unrestricted access to /fauxpay/charge and /fauxpay/refund for arbitrary financial operations.

### [MEDIUM] Duplicate checkout double-submit + non-invalidated token → double billing on single card
**Path:** #14 Missing re-entrancy guard allows duplicate order placement → #7 Card token never invalidated after charge — unlimited replay  
**Blocked by:** requires UI interaction — rapid double-click or queued form-submit events (UI:R in finding 13)

Step 1 — Finding 13: The Checkout submit handler never inspects the current value of submitting before proceeding. In React 18, setSubmitting(true) schedules a state update that only disables the Pay button after the next render flush — which occurs at the first await (tokenizeCard). During the synchronous preamble before that flush, if a second click event fires, a second invocation of submit() executes with submitting === false in its closure. Both invocations pass the addressId check, both call tokenizeCard (generating two tokens, or reusing one depending on the flow), and both call api.checkout(). Step 2 — Finding 15: Even if both checkout calls share the same card token, that token is never deleted from FauxPay's in-memory Map after a successful charge. Both /fauxpay/charge calls succeed against the same token. Two orders are created and two charges are issued against the customer's card for what the customer intended as a single purchase. This is a systematic billing defect, not attacker-driven fraud, but it causes direct financial harm to legitimate customers.

### [MEDIUM] Pre-auth LIKE wildcard DoS + concurrent oversell race + payment-failure stock drain → permanent inventory DoS
**Path:** #12 Unescaped LIKE wildcards in unauthenticated search cause full-table scans → #15 Stock check outside transaction enables concurrent oversell → #6 Stock inventory permanently depleted on payment failure

Step 1 — Finding 2: An unauthenticated attacker floods the catalog search endpoint with crafted LIKE patterns (e.g., q=%a%b%c%d%e%f%g%) that force catastrophic backtracking on Postgres ILIKE for every row, saturating database worker threads and degrading response times application-wide — including for FauxPay charge calls issued by the orders endpoint. Step 2 — Finding 12: Multiple authenticated users (or a single attacker with concurrent sessions) simultaneously submit orders for the same product. The stock-sufficiency check at orders.js:33-39 runs outside the database transaction; both requests pass the check on the pre-decrement snapshot, both enter their transactions, and both decrement stock_quantity — driving it below zero with no floor guard. Step 3 — Finding 8: For each concurrent order where the degraded fauxpay.charge() call times out or errors (induced by finding 2's DB load), the catch block updates order.status to 'cancelled' but never increments stock_quantity back. Each such event permanently reduces inventory. An attacker repeating this sequence with targeted products can drive their stock_quantity to arbitrarily negative values, causing them to display as unavailable and blocking all further purchases — a persistent, low-cost DoS on product availability without completing a single successful purchase.
